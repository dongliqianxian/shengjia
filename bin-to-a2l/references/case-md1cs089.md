# 参考案例:Bosch MD1CS089 / AURIX TC299TP(ISUZU 1.9 RZ4E-TC)

本技能所有阈值都来自这个实测案例。换平台时用它做对照。

**文件**:8,388,608 字节(8 MB)internal flash dump,bench 读取。

---

## ① 容器 ABI 探针 —— 实测数字

```
layout                   endian  width     hits
A_hdr_XY_data                le      2     2189   <- 真实格式
A_hdr_XY_data                le      1     2189   <- 数据宽度歧义
B_hdr_swapped                le      2     1853
E_hdr_YX_data                le      2     1803
D_hdr_pad4_XY_data           le      2      313
C_hdr_data_XY                le      2      162
A_hdr_XY_data                be      2       28   <- 错字节序对照组
```

**判据表现**:对错字节序 **78.2 倍**,对结构性不同的布局 **7–13 倍**。
**残留歧义两个**(探针会自己报出来):

- `A` vs `B`/`E` 只差 1.18 倍 → 行列序 / 轴序分不出
- `A` 的 u8 与 u16 **完全打平**(2189 = 2189)→ 数据宽度分不出,因为轴单调性检验不看数据区

两个歧义都靠**物理量纲**解决:增压图按 u8 读是 0–255(不可能),按 u16 读是 1013–3090 hPa
(绝对进气压力,唯一合理解);转速轴 raw 1200…8000 ÷2 = 600…4000 rpm。

## ② 穷举清单

- 描述符总数 **2189**
- 两轴都识别出来且非平表 **455**
- 分级:`FLAT` 1266 / `CORRECTION` 716 / `BASE` 144 / `MIXED` 63

**平表占一半以上是正常的**——大量是恒值占位(如 8 张恒 500 的轨压占位、恒 8192 的归一化位)。

> ⚠️ **本案例当时的结论已被推翻,保留在此作为教训。**
>
> 我当时据此判定"`0x4B0782` 不是主喷正时,它是修正类"。**错了。**
> 在姐妹文件(ISUZU 120 kW,同发动机)上,厂商工具明确把**同一族、同一值域**的六张表
> 命名为 `Main Injection Base Map 1 #1..#6` —— 它们**就是主喷射正时基础表**。
>
> 根因:粗糙度判据说明的是"**逐格人工优化过**",不是"是修正表"。
> 主喷正时本身就是逐格针对排放和噪声优化的,天生毛糙。
> "平滑=基础表"只对**物理上连续的量**成立,对**排放标定主导的量**不成立。
>
> 仍然成立的部分:**毛糙 ⇒ 整体缩放会抹掉不可复现的台架工作,别乘系数。**
> 详见 SKILL.md 纪律③。

## ④ 物理闭环闸门

厂标 **130 kW / 410 Nm**,1898 cc,4 缸,柴油,η=0.385。

```
     addr    dims    factor   peak mg      kW    err%      Nm    err%   score
0x5314CC  10x10    0.50000     80.00   131.5    +1.2   418.6    +2.1    2.41  <- 假阳性
0x4A8CFC  25x13    0.01000     75.90   132.2    +1.7   397.2    -3.1    3.55  <- 真实燃油上限
0x4E1316  16x16    0.00781     76.56   125.9    -3.2   400.6    -2.3    3.92
```

**闸门 PASS,但真实答案排第 2。** 这就是"短名单不是答案"的实证。
靠维度(25 行覆盖 750–4400 rpm 全转速 × 13 列模式索引)和形态确认 `0x4A8CFC` 才是上限表。

**副产品**:这一步同时证明了 `0x4A8CFC` 的单位是 **mg/stroke(raw/100)**,
而厂商工具 ECM Titanium 把它标成 **Nm**(raw/10 = 759 Nm,对 1.9L 不可能)。

## ⑤ 厂商工具的错误(线索不是证据)

ECM Titanium driver `ISU_4D26` 提供 27 个对象。对照全扫结果:

| 问题 | 实际 |
|---|---|
| 漏表 | 增压漏 5 张、轨压漏 8 张、喷油量漏 6 张 |
| 单位标错 | `0x4A8CFC` 标 Nm,实为 mg/stroke |
| 地址+维度都错 | 烟度限制标 `0x52BF84` 24×25;真实描述符 `0x52BF54` **25×25**,ECM 窗口从第 24 格才开始,前 24 格+最后 1 格够不着 |
| 分组语义 | `[N]` = 往后**连续 N 个结构对象**,不是"副本数",且成员可能不同类(Rail #2 `[2]` 的第 2 个成员是曲线) |

漏掉的往往是峰值最高的那张:增压 `0x4BCA16` 3098 hPa(全文件最高)、轨压 `0x487120` 顶到 1500 bar 限制器。

## ⑥ 反汇编路线的失败记录

Ghidra 12.1.2,`tricore:LE:32:tc29x`,base `0x80000000`(由 AURIX 启动头 `0xB359` + `STAD=0x8000BAE0` 证实)。

镜像分区(由 Ghidra 覆盖率得出):**代码 0x000000–0x3FFFFF / 标定 0x400000–0x5FFFFF / 空 0x600000–0x7FFFFF**。
9,633 个函数入口**全部**落在代码区,覆盖率 85–99% —— 代码没漏扫。

| 尝试 | 结果 |
|---|---|
| 直接 xref 标定地址 | **0/8**(对照组:已证实为真的轨压/增压/驾驶员需求/逆扭矩也全 0) |
| 指针表假设 | **0/8** —— 唯一命中是巧合 |
| `movh.a`+`lea` 全 32 位地址重建 | **0/8**,5077 个恢复目标无一落在标定区 |
| 全指令扫描标定区高半字立即数 | 785,850 条指令中**仅 3 条** |

**结论:该平台标定区不经由代码内立即数寻址,静态反汇编定位不到 map。**
Ghidra 的贡献是:基址确认、镜像分区、以及一个可靠的**否定结论**。

> 这不是 Ghidra 的问题,也不是配置问题——是这类 ECU 的架构性质。
> 在非自描述平台上反汇编路线可能仍然有效,那种情况交 `blind-map-finder` + `ghidra-tricore-disasm`。

67 个 CHARACTERISTIC(63 map/curve + 4 scalar)、123 条轴、7 个分组文件夹,
经独立解析器(`damos-a2l-parser/scripts/parse_a2l.py`)对着 bin 回读验证全部通过。

- ✅ **已证实**:Torque / Injection / RailPressure / Boost 四组

- ❓ **候选**:InjectionTiming(已证实为修正类,主/预喷未分辨)、EGR(形态像,单位未确认)
