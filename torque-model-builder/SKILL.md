# 扭矩基础控制结构模型(Torque-Based Structure)

## 0. 本技能的定位

建模层有两半,本技能是其中一半:

```
air-fuel-model-builder   →  空气/燃油【被控对象模型】(plant): VE / MAF / 喷油器 → 空气质量、脉宽
torque-model-builder     →  扭矩【控制结构模型】(control):   扭矩域 ↔ 负荷 ↔ 空气 的互译与协调
```

**两者不冲突,是严格层级(见 §2)。** 本技能凌驾于 `oem-strategy-library`(那只给各厂命名/限制器
顺序的参考)之上,提供的是"扭矩基础型 ECU 到底怎么想"的第一性原理。运行于 doctrine 黄金顺序之下,
主要服务其第 ⑥⑧ 环(部分负荷/WOT 的扭矩与空气需求)和第 5 节联动清单(TCU/监控)。

---

## 1. 为什么现代 ECU 是"扭矩基础型"

2001 年后(Bosch ME7 起)几乎所有量产 ECU 都是**扭矩基础结构**。原因只有一个:

> **每个想干预发动机的模块都只会说一种货币——扭矩(Nm)——于是它们才能被统一仲裁。**

请求扭矩的来源(全部折算成 Nm 再比较):驾驶员踏板、巡航、牵引力控制(TC/ASR)、变速箱换挡降扭、
空调压缩机、发电机、怠速稳定、催化器加热、各级扭矩限制、ESP。老式(扭矩结构之前)ECU 在
"节气门/空气域"里仲裁,无法干净协调这么多诉求——这就是扭矩结构存在的根本理由。

**第一性原理衔接**:doctrine 原则#1"PCM 不在乎车标"在这里的体现——Bosch/DENSO/Conti/Delphi 的扭矩
结构**骨架完全相同**,只是表名不同(名字查 `oem-strategy-library`)。遇到陌生平台,先映射到本技能的
通用链路,再去找对应表。

## 2. 与"空气优先"的关系(必须先讲清,否则会变陷阱)

doctrine 原则#3:空气流量建模是第一优先级,凌驾一切。**扭矩结构不与它竞争,而是坐在它上面依赖它。**

关键:**负荷(load / 相对充气量 rl)是扭矩世界与空气世界之间的"货币"。**

```
踏板 → 扭矩请求(扭矩域)
   → [逆扭矩模型] → 目标负荷 ────────────┐   ← 空气模型(VE/MAF)在这里把目标负荷变成现实
   → 节气门/增压/凸轮 → 实际空气 → 实际负荷 ┘
   → [正扭矩模型] → 估计实际扭矩 → 反馈 + 监控 + 仪表
```

- 逆扭矩模型的**输出就是一个负荷目标**。空气模型(VE/MAF)负责让"实际负荷 = 目标负荷"精确成立。
- **空气模型错 → 负荷实现错 → 正扭矩模型估计错 → 扭矩监控误触发、燃油/点火全错。** 所以空气优先
  绝对成立。
- 两个世界只在**一个接口**相遇:逆扭矩模型(扭矩→负荷)与正扭矩模型(空气+点火→扭矩)。

**入口铁律(本技能每次任务第一步)**:动扭矩路径任何表之前,先确认空气/负荷模型可信
(VE/MAF 达到 Banish 分档 <5% 可接受 / <3% 理想)。不可信 → 先交 `air-fuel-model-builder`,**不得在坏空气模型上谈扭矩**。
唯一会让"扭矩结构 vs 空气优先"变成冲突的,就是跳过这一步——那是黄金顺序违规,不是两条原则打架。

## 3. 两个扭矩模型(整个结构的心脏)

### 3.1 逆扭矩模型(Inverse / 扭矩 → 空气)
目的:把"要多少扭矩"翻译成"要多少空气"。

```
目标曲轴扭矩
  + 损失回加(摩擦 + 泵气 + 附件: 空调/发电机/水泵)   → 需要的指示扭矩
  ÷ 当前转速下的"单位负荷扭矩"(最优点火、当前 λ)     → 需要的负荷/充气量
  → 目标节气门开度 / 目标增压 / 目标凸轮相位
```
输出 = **负荷目标**,交给空气系统去实现(空气模型在此落地)。

### 3.2 正扭矩模型(Forward / 空气 → 扭矩)
目的:估计"现在实际做了多少扭矩",用于反馈、仪表、和**监控**。

```
M_actual = M_optimal(load, rpm) × η_spark(Δspark) × η_lambda(λ) − M_loss(rpm, …)
```
- `M_optimal(load, rpm)`:最优点火(MBT)、λ 最优时,该负荷×转速能出的指示扭矩(标定表)。
- `η_spark`:点火效率,MBT 时=1.0,点火越退越低(见 §4)。
- `η_lambda`:混合比效率,λ≈0.9 附近火焰最快、扭矩最高(doctrine 数值锚点)。
- `M_loss`:摩擦+泵气+附件损失,把指示扭矩换算到曲轴扭矩。

### 3.3 为什么必须两个模型自洽
逆模型用来**下指令**(定负荷目标),正模型用来**估计与监控**。平台实现可能是分开的正/逆表、
由一张正表运行时反解、共享中间表,或多模型分层切换。先用同版本定义或代码确认架构,不得仅凭表名、
尺寸或"看起来互逆"决定修改方向。

两者是**功能反函数**,不是算术倒数,也不等于固定的 `+10%/-10%`。可用
`R(n,T)=F(n,G(n,T))-T` 检查往返关系,但 OEM 可能有意保留点火/空气扭矩储备、损失和插值余量。
因此先计算 ORI 基线,再判断 MOD 是否让原有关系恶化;不把 `R=0` 或统一 `<3%` 当跨平台写入目标。

只动一边而没有物理依据,可能导致请求负荷、估计扭矩和允许扭矩互相矛盾,最终表现为限扭、
点火/节气门干预、DTC 或 limp。这是 §6 的根。

## 4. 扭矩储备(Torque Reserve)——理解 spark reserve 的关键

ECU 常**故意命令比需要更多的空气(更高负荷),同时退点火**,使实际扭矩仍等于目标:

```
储备扭矩 = M(基础点火) − M(当前退后的点火)
```
被"压住"的这部分扭矩,一旦把点火拉回 MBT 就**瞬间可用**。用途:
- **怠速稳定/防熄火**:负载突增(挂挡、开空调)时,先进点火即可秒补扭矩,不用等进气。
- **催化器加热**:大幅退点火 → 大量热量进排气,同时靠多进气维持怠速扭矩。
- **快速扭矩干预**:点火路径是"快通道"(逐缸即时),空气路径是"慢通道"(进气有延迟)。

标定含义:怠速点火看着"很退"(如 5–10°)往往是**留储备**,不是错——降怠速/改怠速点火前必须
理解这层(与 `idle-speed-calibration` 联动)。

## 5. 扭矩协调(Coordination)= 仲裁 + 快慢两条干预通道

- **仲裁**:对各来源的扭矩请求做 **min 选择**(限制类)/ max 或叠加(某些需求类)。最终扭矩 =
  各限制取最小(doctrine 里 VAG/BMW/DENSO 的"取最小值"就是这一步;具体顺序查 `oem-strategy-library`)。
- **慢通道(空气路径)**:改节气门/增压/凸轮 → 改负荷 → 稳态扭矩。有进气延迟。
- **快通道(点火/断缸路径)**:退点火、断喷/断火 → 毫秒级扭矩下降。换挡降扭、TC 介入、防抖用它。

标定含义:换挡顿挫/降扭深度问题往往在快通道(点火回退量、断缸)+ TCU 请求协议,不在稳态扭矩表
(与 `tcu-shift-calibration` 联动)。

### 5.1 下游闭环消费者的"升级效应"(为什么正模型错会放大成故障)

正扭矩模型的估计值不只喂反馈和仪表,还经扭矩广播供 **ESP/ASR、牵引力控制、TCU** 使用。关键在于
**这些下游是闭环**:它们按你报告的扭矩下发第一次干预量,若你的估计有偏差,第一次干预就不匹配现实,
于是它们**升级**请求,直到达到目标。

因此正模型偏差的实车症状不是"轻微偏移",而是**干预过猛/持续**:

- ESP/ASR:第一次减扭按错误估算下发 → 打滑未消 → 升级到大退角/关节气门/断油(表现为长时间断动力,
  而非闪一下即恢复)。
- TCU:离合器油压、换挡协调、档位保护按错误扭矩算 → 油压欠给、换挡滑摩、保护误动作。

这条把 §6.5"骗扭矩代价清单"从"账面后果"补齐为"动态机制":闭环消费者会把你的估算误差**放大后执行**。
所以正模型的验收标准不止"本机不报错",还包括下游 ESP/TCU 干预是否平顺。Bosch ME7 的 KFMIOP↔ESP
具体变量与实车对照 → `oem-strategy-library` 的 ME7 专项参考。

### 5.2 诊断纪律:执行器振荡 ≠ 扭矩模型错

看到某个执行器(尤其点火角)在巡航/加速时振荡,**不能反推"扭矩模型不匹配"**。最终执行量由多路输入
汇聚:动态爆震控制、爆震学习、暖机/温度修正、扭矩结构目标、外部请求、怠速控制都能让它动。判据是
**分层比较**:基础量 → 各修正 → 扭矩结构目标 → 最终输出;只有当**最终输出跟随扭矩结构目标而偏离
基础量**时,才把线索指向扭矩模型;若偏离由爆震减角或温度修正解释,改扭矩表是错方向。点火路径的
具体变量链(`zwgru/zwbas/zwsol/zwout`)→ `oem-strategy-library` 的 ME7 专项参考。

## 6. 扭矩监控(Monitoring)——头号 Stage 拦路虎

安全概念:一套**独立**的计算持续检查

```
实际扭矩(模型估计)  ≤  允许扭矩(驾驶员想要 + 容差)
```

若在驾驶员没请求的情况下,估计扭矩超过允许扭矩 → 判为"非预期扭矩" → 故障反应(断油/限扭/limp/存 DTC)。
功能层/功能监控层/控制器监控层是通用安全架构。不要把它们直接等同于某个平台文档中名为
"Level 1/Level 2"的扭矩干预阶段。以 Bosch ME7 为例,部分负荷快速点火干预可能属于正常扭矩控制;
节气门强制关闭、DTC、limp 或独立安全监控触发才是必须停止并排查的异常。具体含义以同 HW/SW 的
FR/A2L/DAMOS、状态位和 LOG 为准。

**为什么单表改扭矩会失败(本技能给 stage1 的硬约束)**:要真正抬扭,必须沿**整条路径一致地抬**——
- 驾驶员需求映射(放开请求)
- 最大扭矩限制 / WOT 扭矩限制(抬天花板)
- 扭矩↔负荷换算表两张(逆/正模型保持自洽,否则模型互相矛盾)
- **监控允许扭矩包络/模型副本**(仅在同版本定义证明真实目标域已扩展且该对象需要同步时保形调整)
- 联动:TCU 各档扭矩上限(`tcu-shift-calibration`)、EGT/CAT 热模型是否提前介入

漏掉任何一环 → 要么不生效(被限制器压回)、要么报错限扭。监控调整的目标是让安全检查在新合法
范围继续工作,不是把阈值写满、拍平或关闭。**这就是"改一张表没用"的物理原因。**
具体每张表叫什么、在哪、改多少 → 交 `oem-strategy-library`(命名) + `stage1-calibration-matrix`(矩阵)。

## 6.5 反面: "骗扭矩"(torque model de-rating)的识别与判据

§6 讲的是正面——整条路径一致地抬。实战中遇到的商业程序大量走另一条捷径, 必须能一眼认出来。

### 机制: 一个动作同时干两件事

不同架构的实现不同:有的平台由同一模型运行时反解,有的平台使用独立正/逆表,还有的平台有监控镜像。
先确认架构。常见的低报手法是压低正模型输出;若同一模型参与反解,它还会间接索取更多空气;若正逆表
分开,则通常还会同时抬高逆模型或请求路径。

| 动作 | 效果 | 作用 |
|---|---|---|
| 压低正模型 | 同一真实负荷被估算成更低扭矩 | **这是"骗"的部分** |
| 抬高逆模型/请求负荷 | 同一扭矩请求索取更多空气 | 只有空气、燃油和点火真的增加才可能出功率 |
| 共享模型或运行时反解 | 一次缩放可能同时产生以上两种效果 | 必须由代码/定义确认,不能当通则 |

显示扭矩变低本身不会产生功率。任何收益都来自后续允许了更多真实空气/燃油/点火;若 WOT 已全开、
空气系统饱和或爆震/热保护正在降扭,继续低报不会凭空增加动力。

### 判据: 什么时候是标定, 什么时候是骗

扭矩模型是**物理模型**, 职责是如实描述"这么多空气 → 这么多扭矩"。

- **硬件变了且定义/测量证明单位负荷扭矩关系真的变化**,或工作点进入原模型轴外 → 修正模型让它重新
  对上现实,这是物理模型校正。仅有"换了排气/进气"的清单,没有模型偏差证据,不能自动推出必须改表。
- **硬件没变、物理没变**, 只是想让某个数字低于某条线 → **骗**。那个 −20% 不对应任何物理量的变化。

### 铁证: 独立监控层同不同意

合法模型校正不应要求**关闭**独立监控。但某些软件使用单独的监控模型副本或许可包络;物理关系或合法
目标域改变后,是否需要保形同步取决于同版本定义和代码。"动过监控对象"本身不是骗扭矩的充分证据。

更可靠的判据是:没有物理变化/测量依据却系统性低报扭矩,或把监控阈值拍平、写满、移出使能范围。
真实目标域扩展时允许按已验证关系保形同步监控包络,并保留诊断容差和故障反应;禁止用统一百分比或
满量程常数替代验证。

### 代价清单(必须向客户明示, 不是道德问题是工程问题)

设模型 ×k、实际扭矩 ×m, 则对外报值 ≈ k·m。当 k·m ≈ 1 时报值与原厂几乎一样, 而曲轴实际多出 (m−1):

- **AT/DCT 按 CAN 上收到的扭矩算离合器油压** → 油压被系统性欠给 (m−1), 大负荷打滑与摩擦片磨损
- DSC / 牵引力控制 / 传动系保护全部按偏低扭矩工作
- Level-2 监控被拍平后, 执行器卡滞、传感器漂移时**没有兜底**
- 仪表与诊断读数失真, **后续任何 LOG 诊断都建立在自己骗出来的数上**——这条对调教者自己最麻烦

### 有没有不骗的做法

先看真正瓶颈位于意图层、权限层、模型轴顶还是空气/燃油物理上限。原厂硬件 Stage1 默认优先校正请求
与许可阈值,不改物理模型;硬件改变或进入新充量域时,再按证据扩展轴和校正模型。逆模型自然饱和是否
可接受必须由实际控制链和 LOG 确认,不能假定它与压低正模型"效果相同"。

审计一份现成 MOD 里的这类改动 → `reference-tune-porting`。

## 7. 脚本:scripts/torque_model.py(第一性原理,可自测)

提供扭矩结构的**关系与自洽检查**(逆→正往返、储备=基础−退后、点火效率随退角单调下降),用于
**教学演示 + 解码后 sanity check**,不是替代 ECU 实际标定表。

```bash
python scripts/torque_model.py --selftest
# 逆→正往返:给目标扭矩解出负荷,再正向算回扭矩,应≈原值
python scripts/torque_model.py roundtrip --torque 300 --rpm 3000
# 点火效率:相对 MBT 退 N 度的扭矩比
python scripts/torque_model.py spark-eff --dspark -10
# 扭矩储备:基础点火 vs 退后点火的扭矩差
python scripts/torque_model.py reserve --m-opt 250 --dspark-base 0 --dspark-now -12
```

诚实边界:`M_optimal(load,rpm)`、点火效率曲线、损失都是**标定表**,脚本用的是通用近似
(点火效率用 MBT 附近的钟形/余弦近似),只回答"结构对不对、趋势对不对、数量级对不对",
**具体数值必须以该 ECU 实际表为准**(解码交 bin 引擎,拆解交 `ecu-map-analysis`)。

## 8. 与其他技能的关系

```
torque-model-builder
├── 入口依赖: 空气/负荷模型可信度 ← air-fuel-model-builder (空气优先,不可信先修它)
├── 各厂 MAP 命名 / 限制器顺序 → oem-strategy-library

├── 单表(如逆扭矩表/驾驶员需求表)深度拆解 → ecu-map-analysis
├── 整套抬扭修改矩阵 → stage1-calibration-matrix
├── 在代码里定位扭矩监控/限扭例程 → ghidra-tricore-disasm
├── 换挡降扭/快通道干预/TCU 档位限扭 → tcu-shift-calibration
├── 怠速点火储备 → idle-speed-calibration
├── 字节读写 → bin 引擎;写后 checksum → checksum-crc-engine
└── 所有结论经过 ecu-calibration-doctrine
```

## 9. 输出纪律

- 每次任务**第一步先查空气/负荷模型可信度**(§2 入口铁律),不可信先交 air-fuel-model-builder。
- 区分"需求"与"限制":限制类取最小,漏改任一限制/监控上限则抬扭无效或报错。
- 抬扭结论必须列出**整条路径**要动的环节(§6),不得给"改某一张表即可"的错误简化。
- 具体数值/命名不由本技能出(交 oem-strategy-library / stage1 / ecu-map-analysis);本技能出**结构与因果**。
- 涉及扭矩监控时,必须提示 limp/DTC 风险与 TCU 联动(doctrine 第 5 节)。
- 禁止把平台专用的 Level 1/2 名称直接套成通用三级监控;先确认同版本功能定义。
