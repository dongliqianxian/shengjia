# 已知物理常数定位(physical-constant-locator)

## 先分流:你手上到底有什么

`blind-map-finder` 的入口表已经把"在 bin 里找东西"分了六路。本技能补第七路:

| 你已经有的 | 该用 |
|---|---|
| 只有裸 bin,不知道要找什么形状的表 | `blind-map-finder` |
| **一个**已知数值(限速 250、怠速 800) | `speed-limiter-removal/scripts/value_locate.py` |
| **一组**物理相关的值,或**两个**物理相关的量 | **本技能** |
| DENSO RH850/V850 想要**全表清单** | `denso-rh850-map-inventory` |
| 已知一张表想找它的副本 | `parallel-map-finder` |
| 有 A2L/DAMOS/OLS | `damos-a2l-parser` / `winols-ols-parser` |

**判据一句话**:如果你能说出"这个量和那个量是一套的"(五个档位速比是一套、主减速比和轮胎半径
是一套),就用本技能;如果你只有一个孤立数字,回 `value_locate.py`。

---

## 核心思想:用【关系】定位,不用【数值】定位

单值搜索为什么天生不行:`0x0E8F`(3727)这种两字节模式在 736 KB 里出现 7 次,`0x0186`(390)
出现 77 次,`0xFA`(250)满地都是。你无法从数值本身分辨真伪。

三条"关系"比数值强得多:

### 1. 尺度无关的向量指纹【最强】

标定的定点标度未知(Q8/Q10/Q12/×100/×1000…),但**一组值的形状与标度无关**。把候选和目标
各自除以自身均值再比对,标度自动消掉。

> 实测:丰田 FJ 4.0(DENSO V850,736 KB),用 A750F 五速速比 `3.520/2.042/1.400/1.000/0.716`
> 加倒挡 `3.224` 做指纹,**全片只命中 1 处**(`0x00F8F4`),误差 0.06%。

而且**标度是副产品**:命中后 implied scale = 4097 → 你顺带知道了这个 bin 用 **Q12(1.000=4096)**。
后面所有别的常数都能用这个标度去读。

它还能**顺带判定车型变体**:能匹配上 A750F 五速速比,就说明这是自动挡标定,不是手动挡。

### 2. 共享标度的联合约束

同一族的常数**共用一个标度**,这是物理事实,不是巧合。要求两个量落在同一窗口内、用**同一标度**
解码,比分别搜两个值强得多。

**关键纪律:能给精确值就别只给带。**
- `--joint name=lo:hi`(物理带)= **漏斗**,给你几十上百个候选让你看。
- `--expect name=value`(精确期望值)= **判别器**,直接出答案。

你通常是知道候选值的——你的车不是 3.727 就是 3.909 或 4.10。实测用 `--expect` 全片只出 1 个命中。

> ⚠ 别指望排序能救只给带的搜索。原始值分布**极不均匀**(小整数遍地),所谓"带越窄越可信"的
> 先验推理是错的。本脚本用**经验意外度**(实际命中率)而非先验带宽排序,但即便如此,只给带
> 仍然只是漏斗。

### 3. 唯一性 = 可写进报告的证据

拿到候选后做唯一性检验,把"看起来对"变成"排除巧合":
- 拼接字节签名在全文件出现几次?
- 两两共现在全文件出现几次?

> 实测:`86 01 8F 0E 06 0A` 在 736 KB 中**出现 1 次**;3727 与 2566 相距 16 字节内的组合
> **全文件仅此一处**。这是可以写进交付报告的陈述。

**但唯一性只排除巧合,不证明语义。** 到这一步还是"高可信候选"。

## 脚本

```bash
S=physical-constant-locator/scripts/invariant_locate.py

# 1) 向量指纹:找变速箱速比表(顺带解出定点标度)
python $S --bin ECU.bin --vector 3.520,2.042,1.400,1.000,0.716,3.224 --label A750F

# 2) 判别器:已知主减速比与分动比的精确值 + 轮胎半径的物理带,共享标度
python $S --bin ECU.bin \
    --expect final_drive=3.727 --expect xfer_low=2.566 \
    --joint tyre_r=0.35:0.43 \
    --scales 1000,4096,1024,256,100 --window 24

# 3) 证据化
python $S --bin ECU.bin --verify 0xFA20:390,0xFA22:3727,0xFA24:2566

python $S --selftest
```

常用开关:`--dtype u8|u16|u32`、`--endian le|be|both`、`--tol`、`--steps 2,4`(u16 打包 vs 落在
4 字节记录里)、`--align 1`(未对齐数据)。向量模式默认也试**倒序**(有些 ECU 从高档存到低档)。

## ⚠ 最大的坑:全局基址寄存器(xref 全落空时看这里)

**症状**:你确信地址是对的,但 Ghidra 全量分析对目标地址 `refs=0`;搜 `movhi/movea` 构造地址的
模式零命中;搜 32 位地址字面量零命中。于是你开始怀疑地址错了。

**真相**:很多 ECU **根本不逐处构造地址**。编译器把一个基址常量在复位路径里装进一个寄存器,
此后全程用 `基址寄存器 + 16 位位移` 访问标定。位移不等于地址,所以按立即数搜什么都搜不到。

> 实测:丰田 FJ(V850)在 `0x0001A4AA` 执行 `mov 0xE010, tp`,此后所有标定访问都是
> `ld.h <disp>[tp]`。**绝对地址 = 0xE010 + 位移**。找到这一条之前,Ghidra 对 5 个目标全部
> `refs=0`;找到之后,`0x00FA20` 立刻显示出 **11 处读取点**。

### 解锁流程(四步)

1. **从复位向量走真正的启动代码**,不要在数据区线性反汇编(数据当代码解会产生大量假的
   "写 gp/tp" 指令,`fetrap`、`satsub ep,tp` 这类怪指令就是误解码的标志)。
2. 在启动路径里找**给基址寄存器装常量**的指令。V850/RH850 是 `mov <imm32>, tp|gp|ep`,
   通常紧跟在中断优先级初始化之后。
3. **绝对地址 = 基址 + 有符号位移**。用它重算全部 `ld/st <disp>[基址寄存器]`。
4. 用 **读/写属性**区分两个基址:只被 `ld` 读的基址指向 **flash 标定**;有 `st` 写入的指向 **RAM**。
   这是最快的区分法。

### 各核的基址寄存器(动手前先确认)

| 核 | 常用全局基址寄存器 | 备注 |
|---|---|---|
| **V850 / RH850** | `gp`(r4)、`tp`(r5)、`ep`(r30) | 本次实测:tp=flash 标定,gp=RAM |
| **TriCore** | `a0`/`a1`(小数据)、`a8`/`a9`(应用) | 同理,`ld.w d0,[a0]off` 的 off 不是地址 |
| **SH-2/SH-2A** | `GBR`,以及 PC 相对常量池 | SH 更多用 PC 相对 literal pool |
| **PowerPC** | `r2`(TOC/SDA2)、`r13`(SDA) | 小数据区锚点 |

工具链搭建见 `ghidra-ida-setup`(已补入本节的跨核速查),反汇编分析见 `ghidra-tricore-disasm`。

## 从【算术用法】反推语义角色

地址对了还不够——**哪个是半径、哪个是速比?** 不要靠数值猜,靠代码怎么用它:

| 代码怎么用 | 说明这是什么 |
|---|---|
| 作**乘数**,且出现**自乘平方** | 无量纲**传动比**(比值平方 = 惯量折算) |
| 作**除数**,且出现**自乘平方** | **长度量**(半径;÷r = 扭矩→力,r² = 惯量折算) |
| 与转速相乘后再除以常数 | 参与**车速/角速度**换算 |
| 被 `基址 + 索引×2` 访问 | 是**表**不是标量(索引是档位/缸号/模式) |
| 出现 `mulhi 0x3E8`(×1000)等 | **印证定点标度**,与你解出的标度对不上就是解错了 |

> 实测:`FUN_00060c16` 里 `0x00FA22` 被当乘数并自乘 → 速比;`0x00FA20` 被当除数并自乘 → 长度。
> 同一函数算出 `主减速比²/半径²`(整车质量→发动机端等效惯量的标准式),两者角色不可能互换。
> 另有 `ld.h <off>[tp + 档位×2]` 按档位索引速比表,独立印证了向量指纹的判定。

**同一函数同时读取多个常数 = 它们属于同一物理模型**,这是最强的分组证据。

## ⚠ 冗余编码:同一物理量可能存了不止一份

ECU 常把同一个量**预算好存多份**以省运行时开销。

> 实测:轮胎存了两份——`0x00FA20` 半径 0.390 m(×1000),`0x00F82A` 滚动周长 2.4500 m(Q12)。
> 二者互推差 0.02%。

两个后果,都重要:
1. **正面**:两份独立编码互相吻合 = 一条独立的交叉验证证据。
2. **风险**:**改一份漏一份,ECU 内部两套假设打架**。改动前必须把同族冗余编码找全
   (用 `--expect` 把派生量也搜一遍,或用 `parallel-map-finder` 找副本)。

### ⚠⚠ 但"吻合"可能是巧合 —— 必须用【跨文件对照】证伪

上面那条实测,后来被推翻了一半,教训值钱:

> `0x00F82A` = 10035,Q12 解得 2.4500 m,与 2π×0.390 = 2.4504 m 只差 **0.02%**,
> 而且就在读半径的同一个函数里。看起来铁证如山。
> 拿**同平台另一台车**(89663-60U70,轮胎半径 0.381 m、主减速比 4.100)一对照:
> 对应槽位的值**一模一样还是 10035**。轮胎不同而值相同 ⇒ 它根本不是周长,
> 是个**固定代码系数**。0.02% 的吻合纯属巧合。

**判据(强烈推荐,成本极低):**
拿同平台、不同车型的第二个标定文件,把同一条指令序列读到的各个槽位逐一对比:

| 跨文件表现 | 结论 |
|---|---|
| **值不同** | 整车参数(可能需要跟着改) |
| **值相同** | 代码系数(**不要动**) |

没有第二个文件时,退而求其次:该量若真是派生量,换一台车/换一条胎它必须变;
**单文件内的数值吻合永远不足以证明派生关系**。

这条同时修正了证据分级:L4"冗余编码互证"必须由跨文件对照背书,否则只算 L3。

## 证据分级(输出时必须标明到哪一级)

| 级 | 达成条件 | 能怎么说 |
|---|---|---|
| L1 候选 | 数值落物理带 | "候选" |
| L2 强候选 | 向量指纹命中 / 共享标度联合命中 | "高可信候选" |
| L3 排除巧合 | 字节签名 + 共现在全文件唯一 | "排除巧合,仍待代码证实" |
| L4 物理自洽 | 冗余编码互证 + 实车物理量核对 | "自洽" |
| **L5 事实** | **代码读取点 + 算术用法定角色** | **"已证实"** |

**没到 L5 一律说"候选"**(doctrine 第一陷阱:"对了但理由错了")。

## 分工(defer,不越界)

- 本技能:定位**已知名字的物理常数** + 出证据等级。
- 不猜未知 map 形态(`blind-map-finder`)、不出全表清单(`denso-rh850-map-inventory`)、
  不搭反汇编工具链(`ghidra-ida-setup`)、不做通用限制器逻辑分析(`ghidra-tricore-disasm`)。
- 字节读写 → `denso-bin-engine` / `bosch-conti-bin-engine`(字节序先经 `multi-vendor-ecu-engine`)。
- 单表功能判定 → `ecu-map-analysis`;换算 → `winols-scaling-converter`。
- **写盘后 checksum → `checksum-crc-engine`;未重算 checksum 的文件一律不得称"可刷写"。**

## 输出纪律

- 给地址必须同时给**证据等级**和**怎么确认的**(指纹误差 / 唯一性次数 / 读取点数 / 算术用法)。
- 只给带的联合搜索结果永远称"候选清单",不称答案。
- 标明地址是**文件偏移**还是加了镜像基址的真实地址。
- 改动建议必须附**同族冗余编码清单**(见上节)与 checksum 闸门。
