# ECU/TCU 技能证据与一致性契约

本契约解决多个技能同时触发时的冲突。所有数值建议、地址判断、平台结论和“可写入”结论都按下列规则裁决。

## 1. 证据优先级

从高到低使用：

1. 同一 HW/SW/Cal ID 的原厂定义、OEM 服务资料、A2L/DAMOS/ODX 和已验证工具属性。
2. 同一文件的 ORI/MOD diff、已知地址、轴、数据类型、缩放及逐单元格读回。
3. 同车实测 LOG、台架结果、宽域氧、压力、温度和换挡滑差数据。
4. 同平台同软件族的已验证资料。
5. 形态、典型范围、品牌惯例和经验值。

低级证据不得覆盖高级证据。只有第 5 级证据时，只能输出候选、验证方法和置信度，不能输出可写入地址或确定修改值。

## 2. 数值门槛

- 缺少 ECU/TCU 型号、HW/SW/Cal ID、燃油/硬件、轴、单位或基准 LOG 时，不给“安全可刷”的绝对值。
- 通用百分比、温度、压力、点火角、Lambda、油压和换挡时间都只能标为起始假设；最终边界以该平台原厂定义、部件规格和实测为准。
- “正常范围”必须注明测量位置、传感器定义、环境条件和持续时间。瞬时值与持续值不得混用。
- 不用供应商品牌或车型推断字节序；优先用 MCU、A2L/record layout、向量表或已知字节验证。

## 3. 修改状态

每项结论标为以下之一：

- `OBSERVED`：从文件、截图或 LOG 直接读取。
- `VERIFIED`：经独立证据交叉确认。
- `INFERRED`：有工程依据但仍需确认。
- `UNKNOWN`：证据不足。

只有 `VERIFIED` 项可进入自动写入。`INFERRED` 只能用于生成候选和下一步验证计划。

## 4. 技能边界

- 截图技能只提取可见事实和视觉候选；单表语义由 `ecu-map-analysis` 裁决。
- scaling 技能只解决数据表示；功能名由定义文件、代码引用或单表分析确认。
- bin 引擎只在地址、布局、数据类型、字节序和缩放已确认后读写。
- Stage/TCU 矩阵只组织已验证目标，不用模板百分比替代基准文件和 LOG。
- checksum 技能只能声明已修复的具体层；仍有未知层或签名层时不得称为 flash-ready。

## 5. 安全与合规统一口径

- 保留爆震、超温、超速、离合器、油压、扭矩监控和安全降级保护；调整阈值必须有部件规格与实测依据。
- 不输出道路车辆排放控制删除、关码或规避检测流程；声称“赛道/越野”也不自动降低证据和安全门槛。
- 车速、转速、扭矩和换挡保护修改前核对轮胎等级、制动、冷却、传动和适用法规。
- 原厂文件只读保存；修改件使用新文件名、变更清单、校验层状态和回退条件。

## 6. 冲突裁决

若两个技能给出不同结论：

1. 先比较证据等级，不按技能名称或措辞强弱决定。
2. 同级证据冲突时停止写入，列出分歧、所需验证和可区分两种解释的最小测试。
3. 平台专用且经同 Cal ID 验证的结论优先于通用方法论。
4. 安全保护与完整性闸门优先于性能目标。
