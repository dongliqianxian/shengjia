## 一、刻度（scaling / LSB）的证据门槛

### 1.1 不许反向拟合 LSB —— 有实证案例

**规则**：先选一个让数字变漂亮的刻度、再拿"漂亮"当证据 = 循环论证。

**实证（5eat §11i → §11s）**：他们给转速轴定 `x/12.8`，理由是"12.8 = 64/5，是一个看起来合理的定点除数"。
后来被推翻，真值 `x/8`，**错了 1.6 倍**。修正后断点变成 640 RPM 一步、6400 封顶、8192 哨兵；
他们自己的评价是"旧估算的 4000 RPM 天花板对这个发动机家族从来就说不通"。

**教训**："这个除数看起来合理"不是证据。它只是让你更难发现自己错了。

### 1.2 刻度需要两条独立证据，至少一条来自代码

**升级自原纪律 #3**（原规则只说"必须来自外部锚点"，没说要几条）。

外部锚点分两类，**必须各有一条**：

| 类 | 例子 |
|---|---|
| **外部权威** | 厂家维修手册数据、已知变量 scaling、共用同一轴数组的已知表、同平台 A2L |
| **固件自身算术** | 反汇编/反编译里显式的 `/0x400`、`<<3`、`× 常量`；共享的钳制常量 |

**实证（5eat §11r）**：齿比表 `/1024` 同时被两条确认 —— 维修手册公布的 5EAT 齿比
（3.540/2.264/1.471/1.000/0.834，误差 <0.0007）**和** 固件自己的 `(DAT_008082ba * DAT_0001234c) / 0x400`。
这是那个项目里第一个真正证实的刻度，前面所有的都只是标了 "(est.)" 的结构性猜测。

### 1.3 共用步长 ≠ 共用单位（修正原纪律 #2 的边界）

**原纪律 #2**：步长分布是判轴第一判据 —— 低端加密=踏板/负荷/扭矩类；低端粗高端细=转速类。**仍然成立。**

**必须加的边界**：步长分布只能定**类别**，不能定**同一性**。

**实证（5eat §11s 第二处修正）**：`0x0117BE` 被标成 RPM，纯粹因为它共用了 5120 的断点步长约定。
重查实际输入链，发现是完全不同的信号（`<<8` 的 0-255 字节，不是 `<<3` 的速度信号）。原文：

> **共用步长间距不是共用单位的证据 —— 这个错误不值得再犯一次。**

### 1.4 "(est.)" 标记要落进交付物本身

置信度分级不能只活在对话里。凡是估算的刻度，**在 XDF / def / 表格文件里就带 `(est.)` 后缀**，
等代码或外部权威证实了才删。下次打开文件就知道哪些能信，不必回翻聊天记录。

## 二、候选确认

### 2.1 指针命中是确认过滤器，不是第五类候选

**做法**：盲扫出的形态候选，用"ROM 里别处有 32 位绝对指针指向其表头"来分层，不要平铺输出。

**实证（5eat §3）**：307 个模式候选中，只有 **38 个**有真实指针引用指向表头精确偏移。
这 38 个是高置信；其余 269 个明确标为"未确认，可能是真表，也可能是代码里的巧合单调段"。

### 2.2 并列数组的间距就是长度

若干数组紧密相邻排列时，**相邻数组起址之差 = 单个数组长度**。

**实证（5eat §11r）**：五个位模式数组差点按 8 条目发出去，靠"每个正好隔 14 字节"抓住，真长度是 14。

### 2.3 全是 2 的幂 = 位模式，不是标量

数据全部落在 0/1/2/4/8/16/32/64/128 上时，它是**位掩码**，不是数值表。
按标量去插值或缩放会产生无意义的中间值。这类表在交付物里应标为专家级 + 明确警告。

## 三、反汇编 vs 反编译（对 `ghidra-tricore-disasm` 是硬约束）

### 3.1 反编译产物不能用来回答关于指令流的问题

**实证（5eat §46，标题就叫 "THIS PROJECT HAD NO DISASSEMBLY"）**：
该项目 20 个章节关于 Denso 代码的结论全部读自 Ghidra 反编译伪代码，仓库里根本没有反汇编清单。
结果错了，因为反编译器**按设计**会：

- **丢掉字面量池** —— PC 相对加载读的常量被折叠进表达式或直接丢弃
- **未被引用的常量拿不到符号** —— 在 C 里根本搜不到
- **PC 相对加载变成裸符号名** —— 看不出关键值是 ROM 地址的**内容**还是地址本身

量化：同一个问题，从反编译 C 里 recover 出 **401** 个 RAM 地址；从真正的反汇编清单 **2848** 个。原文：

> 不是因为那个方法错了，而是因为它在问一个已经把答案丢掉了的产物。

**规则**：找 scaling、找常量、找字面量 → **必须走反汇编清单或原始字节**，不能只用反编译输出。
ReVa 一类 MCP 工具同理：`ConstantSearch` / `Memory` 类工具优先于 `Decompiler` 类工具回答刻度问题。

### 3.2 把表当代码反汇编会制造假交叉引用

**实证（5eat `tools/denso_data_ranges.py`）**：

> 完整反汇编需要知道**不要**反汇编什么。把表解码成指令会毁掉它，更糟的是**制造出看起来很真的交叉引用**
> —— 一次忽略了这点的扫描产生了 77 个指向换挡表数组的引用者，每一个都是扫描在读它自己错误解码出来的指针。

**规则**：盲扫与反汇编"互相印证"的前提是两条腿独立。
**先输出数据区范围表喂给反汇编器让它跳过**，否则两条腿会互相污染，而且污染的结果看起来是强证据。

## 四、功能判定的实验方法

### 4.1 扰动法：改一个值，看什么动了

调用图密到无法区分时（"三个函数各发布 48 个命名值，什么都连到什么"），别再追链路，直接问：
**改 ROM 里的表 → 跑同一段工况 → 对比整个 RAM/log 的差异。动了什么就是这张表影响什么。**

原作者的评价："这本该是第一个方法。" 同样的思路在 CAN 信号映射上找到了真信号，
而扫描输入的方法产生了 1118 个假阳性。

**限制**：驾驶工况没触及的表不会动，报告为"无影响"而不是"无意义"。所以要跑多组工况
（怠速 / 巡航 / 加速 / 强制降档 / 油温高）。

### 4.2 零基线陷阱

> RAM 清零时每个比较都走默认分支，所以一个函数可能对任何**单个**输入看起来都无反应，
> 却对一个合理的状态响应良好。一次探一个变量是错误的实验，这个错误造成了几次错误结论。

**正确顺序**：先全零 vs 全高，确认函数是否真的输入无关 → 动了再逐个二分找出承载效应的那个。

## 五、负面结论（doctrine 原本的空白）

**"某个东西不在这个文件里"是一个合法的、可交付的结论**，而不是"还没找到"。

### 5.1 如何证明

**实证（5eat §12d，线压 kPa 单位）**，四组独立测试：

| 测试 | 结果 |
|---|---|
| 手册 kPa 值作为代码立即数 | 11 个固件全部 0 命中 |
| 跨该压力带的单调标定段 | 只有已知的速度表 |
| 记录式曲线的值域扫描 | 一个候选，512-2048，是 2 的幂 → 缩放表 |
| 490 与 1370 同时出现在标定区 | **11 个固件里只有 1 个** |

**决定性的是最后一条**：那两个数是同一台变速箱的规格值，全系通用。TCU 若存了它们，
11 个固件应该都有。只有 1 个有 —— 原文：**"11 个里出现 1 次，正是 384KB 里概率该产生的结果"**。

### 5.2 交付负面结论必须包含

1. **做了哪些独立测试，各自结果** —— 不是"我找过了"
2. **决定性判据是什么** —— 上例是"跨固件一致性"，比任何单文件搜索都硬
3. **代码覆盖率检查** —— 他们确认反编译覆盖 1056 个函数、跨越 0x000168–0x05F4C4，
   每个 >2KB 的空隙都是已知空白区或 bank 填充。**"这个转换没有藏在未分析的代码里。"**
4. **最可能的解释** —— 上例：转换在诊断仪侧做，TCU 只报原始值
5. **什么才能真正解决** —— 上例：SSM 参数定义，或实车对照记录。
   **"两者都需要硬件。这不是静态分析问题，继续搜 ROM 不会有结果。"**

### 5.3 "证据不足"是终态，不是降级的结论

来自 CSS Electronics CAN skill 的验证纪律：低 R²、候选分数接近、可信度标记触发时，
输出判 **UNCONFIRMED**，要求重新采集数据，**不给一个勉强的答案**。

对应到标定：与其给一个带三行警告的地址，不如明确说"当前证据不足以定位，需要 X"。
带警告的错答案会被使用，明确的"不知道"不会。

## 七、校验和（doctrine 校验和交付闸门——黄金顺序⑬前置，交 `checksum-crc-engine` 执行）

以下全部来自两个真实实现，**不是推测**：

### 7.1 校验区范围必须逐镜像检测

**实证（5eat `tools/checksum.py`）**：同一个 TCU 家族里两种约定并存 ——
`0x60000` 固定长度（含 512KB 镜像里只用 384KB、尾部留空的情况）与"整个文件"。原文：

> 假定任何一种都会在一半的家族上产生一个自信的错误答案。

**做法**：把候选范围都算一遍，**哪个能复现 ROM 里已经存着的值，哪个就是这个镜像的约定**。

### 7.2 可能存在第二个独立校验和

同一家族每个镜像还带一个 `0x008020` 的 "balance"，而且**分 16 位与 32 位两种变体**：

- 32 位：全和必须等于 `0x5AA5A55A`，balance 是 `0x008020` 整个 32 位字
- 16 位：只检低半，对 `0x5AA5`，balance 是 `0x008022` 的半字，`0x008020` 保持零

**16 位那种最容易漏**，漏了就是 11 个 ROM 里 8 个改完过不了自检。
判别是结构性的（16 位镜像在 `0x008020` 半字处是零），改完仍然成立。

**顺序**：balance 在附加校验和覆盖的区域内，附加校验和的槽位在 balance 区域外
→ **先修 balance，后修附加校验和，一遍收敛**。

### 7.3 Bosch MED17/EDC17 的块发现锚点

**实证（medc17-checksum-tool）**：每个块的第一个 32 字节校验结构固定在 `block_start + 0x34`，
其中 `+0x0C` 是种子 `0xFADECAFE`，`+0x10` 是期望值 `0xCAFEAFFE`。
**1/2⁶⁴ 的锚点** —— 直接搜这对魔数定位所有块，不要猜。

- 块类型字节在 `block_start + 15`：`0x80` = 应用（缓存 flash 视图），`0xA0` = 数据/标定（非缓存）
- **TriCore 地址别名**：同一物理 flash 映射成缓存 `0x8xxxxxxx` 与非缓存 `0xAxxxxxxx` 两个视图。
  转文件偏移前必须剥掉段 nibble，**否则 0xA0 块会偏出 0x20000000**
- 未编程分区把校验/调整字段留成重复填充字节（`0xFF` 或某些 Bosch 镜像的 `0xAF`）→ 没有真东西要保护，修正必须跳过
- CRC32 可用 GF(2) 矩阵代数瞬时求解：往一个擦除态 dword（`0xFF` / `0x00` / Bosch pad `0xC3`）写补偿值
- **多变体**：有多个标定变体的 ECU 维护每变体参数地址表，监控校验和是对**当前激活变体**算的
  —— 只修第一个，其余全错

## 八、反面教材（禁止模仿的具体做法）

来自 `wexcomm/hp-tuners-ai-agent` 的实际代码，作为"臆造"如何伪装成"能跑的代码"的样本：

1. **自造格式的往返自洽**：`HPTHeader` 自己定义魔数 `HPTF` 与 256 字节布局，
   `to_bytes()` 按它写、`from_bytes()` 按它读。往返完美 —— **因为两头都是它自己造的**。
   真实 `.hpt` 文件进去会在魔数检查处直接返回 None。整个仓库**没有一个真实样本文件**。
   → 对应 doctrine §6.2 禁止臆造。**代码能跑、测试能过、往返自洽，都不构成格式正确的证据。**

2. **圆整数字的功能分区**：`0x20000-0x50000 Engine Tables`、`0x60000-0x70000 Fuel Tables`、
   `0x80000-0x90000 Torque Model`……真实 flash 不会按功能切成整齐的 64KB 块。
   **而且同仓库内自相矛盾** —— 另一个文件说 `0x80000` 是校验和槽位。

3. **按控制器名查固定校验区**：正是 7.1 明确警告的做法。
